# Cross-cloud routing

How shimanism translates a request from one cloud's tools into a call against a different cloud's services, with minimal overhead.

> Read this alongside [PHILOSOPHY.md](../PHILOSOPHY.md) (the *why*) and [services/storage/OPERATIONS.md](../services/storage/OPERATIONS.md) (the per-operation equivalence table).

## Terminology

- **Frontend** = the client tool issuing requests to the shim. Per cloud:
  - AWS: `boto3`, `aws-sdk-go-v2`, `aws-sdk-java`, `aws-sdk-js`, `aws` CLI, `hashicorp/aws` Terraform provider.
  - GCP: `cloud.google.com/go`, `google-cloud-storage` (Python), `@google-cloud/storage` (Node), `gcloud` CLI, `hashicorp/google` Terraform provider.
  - Azure: `azure-sdk-for-go`, `azure-storage-blob` (Python), `@azure/storage-blob` (Node), `az` CLI, `hashicorp/azurerm` Terraform provider.
- **Backend** = the SDK/library the shim imports internally to drive the destination cloud. Same set of libraries, used in the opposite direction:
  - `backends/aws/` imports `aws-sdk-go-v2/service/s3` and calls real AWS S3.
  - `backends/gcs/` imports `cloud.google.com/go/storage` and calls real GCS.
  - `backends/azureblob/` imports `azure-sdk-for-go/sdk/storage/azblob` and calls real Azure Blob.
  - `backends/minio/` imports `minio-go` and calls a MinIO instance (S3-compatible).
  - `backends/k8s/` uses `controller-runtime` + an operator-managed peer (MinIO-in-cluster, CloudNativePG, etc.) for the Kubernetes-as-fourth-backend pattern.
- **Opposite-shape** = the shim's *value* shows up when **frontend-cloud ≠ backend-cloud**. A `boto3` client (AWS-shape) drives the shim, and the shim's `backends/gcs/` (GCS-shape) drives real GCS. The two shapes meet at the domain layer.

## The matrix

Per service (object storage in this doc; secrets, queue, etc. follow the same pattern):

```
                              backend
              AWS S3    MinIO    GCS    Azure Blob   K8s peer
            ┌──────────────────────────────────────────────────
AWS S3 wire │ pass     pass     ★      ★            via K8s op
GCS wire    │ ★        ★        pass   ★            via K8s op
Azure wire  │ ★        ★        ★      pass         via K8s op
            └──────────────────────────────────────────────────

pass = passthrough (frontend cloud == backend cloud)
★    = real cross-cloud translation
```

The shim deployment picks one column at config time. Each frontend protocol serves every column.

### Layers

| Layer | Owned by | Job | Lines of Go (est.) |
|---|---|---|---|
| Wire codec | codegen output (one per source cloud) | XML/JSON decode → typed `gen.*Request`; symmetric for response | autogenerated |
| Frontend adapter | `internal/storage/frontends/<cloud>/` (one per source cloud) | translate `gen.*Request` ↔ `domain.*` | ~300 each |
| Domain interface | `internal/storage/domain/` (one total) | neutral types + `Storage` interface | ~150 |
| Backend | `services/storage/backends/<cloud>/` (one per destination cloud) | `domain.*` ↔ cloud's native API | ~400 each |
| Probe handling | frontend adapter | `GetBucketTagging` (etc.) returns "not configured" without going to the domain | included in adapter |

**Total: 3 + 1 + 4 = 8 hand-written files of meaningful code per service**, regardless of how many client tool flavors target each cloud. Compare to a per-pair approach: 3 × 4 = 12 files, growing quadratically.

## Performance

The architecture is designed to add minimal overhead per request. The targets:

- **Object body bytes are streamed, never buffered.** `httpPayload` blob members are `io.Reader` for inputs (set directly to `http.Request.Body`) and `io.ReadCloser` for outputs (copied with `io.Copy` straight to the response writer). The shim never holds an object body in memory; multi-GB uploads / downloads go through unchanged in size.
- **Metadata is small and copied once.** Headers and small XML body documents (lifecycle configs, ACLs, etc.) buffer in memory, but the volume is bounded by the operation, not the data.
- **No double-encode / double-decode.** The wire codec deserialises bytes once into typed structs; the frontend adapter does field-by-field translation into domain types (no JSON/XML re-trip); the backend translates domain to its native call type (also field-by-field).
- **Backend HTTP clients pool connections.** Each backend (`backends/aws/`, `backends/gcs/`, …) reuses its underlying SDK's HTTP client, which manages persistent connections, keep-alives, and HTTP/2 multiplexing to the destination cloud's endpoints.
- **Handlers are stateless and concurrent.** The shim itself holds no per-request state beyond the goroutine stack; `net/http` schedules one goroutine per incoming request.

### What this rules out, on purpose

- **No request buffering.** A handler that reads the whole request body before calling the backend is a bug.
- **No response materialisation.** A handler that builds the entire response in memory before writing is a bug for blob-payload responses.
- **No background workers for translation.** Translation happens inline on the request goroutine; the only goroutines spawned by the shim are those `net/http` creates per request and the SDK's connection-pool internals.

### What this requires

- The codegen, for input members with `httpPayload` targeting a blob, emits `Body io.Reader` (not `[]byte`) and sets it to `r.Body` directly.
- The codegen, for output members with `httpPayload` targeting a blob, emits `Body io.ReadCloser` and the response-encoder uses `io.Copy(w, out.Body)` then `out.Body.Close()`.
- The domain interface's `GetObject` returns `io.ReadCloser`; `PutObject` accepts `io.Reader`.
- Each backend's PUT path passes the reader straight through to the cloud's SDK upload call (which all support streaming); GET path returns the cloud SDK's response body reader.

## Implementation order (Phase 1.5 onwards)

The refactor lands at the start of Phase 1.5, before MinIO is wired, so MinIO is the first backend designed against the domain.

1. **`internal/storage/domain/`** — types + `Storage` interface (streaming-friendly). ~150 lines.
2. **`internal/storage/frontends/aws_s3/`** — adapter implementing `gen.AmazonS3Backend` by wrapping a `domain.Storage`. Pulls the wire-translation logic out of `services/storage/backends/inmem/`. ~300 lines.
3. **Refactor `services/storage/backends/inmem/`** — implements `domain.Storage` directly. Drops the `gen.*` types. Shrinks ~700 → ~400 lines.
4. **Codegen streaming changes** — `httpPayload` + blob → `io.Reader` / `io.ReadCloser`. Conformance suite still passes against the in-mem backend (which now consumes/produces streams).
5. **`services/storage/backends/minio/`** — implements `domain.Storage` using `minio-go`. First real backend on the domain interface. Conformance suite runs against it (Docker-based MinIO in CI).
6. **`services/storage/backends/aws/`** — passthrough using `aws-sdk-go-v2/service/s3`. Same operations, against real AWS S3 (nightly tier; recorded interactions for PR-time).
7. **`services/storage/backends/gcs/`** — first cross-cloud translation. AWS-shape coming in (via the aws_s3 adapter → domain) → GCS-native calls.
8. **`services/storage/backends/azureblob/`** — same shape for Azure.
9. **`services/storage/backends/k8s/`** — Kubernetes peer; likely MinIO-in-cluster managed by an operator.

## Per-operation translation example

`services/storage/backends/gcs/list_buckets.go`:

```go
func (b *Backend) ListBuckets(ctx context.Context, opt domain.ListBucketsOptions) ([]domain.Bucket, error) {
    it := b.client.Buckets(ctx, b.projectID)
    if opt.Prefix != "" {
        it.Prefix = opt.Prefix
    }

    var out []domain.Bucket
    for {
        attrs, err := it.Next()
        if errors.Is(err, iterator.Done) {
            break
        }
        if err != nil {
            return nil, translateGCSError(err)
        }
        out = append(out, domain.Bucket{
            Name:      attrs.Name,
            CreatedAt: attrs.Created,
            Region:    attrs.Location,
        })
        if opt.MaxResults > 0 && len(out) >= opt.MaxResults {
            break
        }
    }
    return out, nil
}
```

That's it. No XML decoding, no header parsing — the wire codec already did that. No "what if the client wants AWS-shape" — the domain interface IS the contract; whichever frontend called us has already translated to the domain. The backend is a pure GCS adapter.

## How the bucket-config probes flow

The 18 `GetBucket*` probes added in Phase 1.4 (GetBucketPolicy, GetBucketTagging, …) are S3-protocol-specific and not part of the domain. They live in the AWS frontend adapter:

```go
// internal/storage/frontends/aws_s3/probes.go
func (a *Adapter) GetBucketPolicy(ctx context.Context, in *gen.GetBucketPolicyRequest) (*gen.GetBucketPolicyOutput, error) {
    if _, err := a.storage.HeadBucket(ctx, in.Bucket); err != nil {
        return nil, err // domain Storage already returns NoSuchBucket
    }
    return nil, restxml.NoSuchBucketPolicy(in.Bucket)
}
```

The adapter checks that the bucket exists (via the domain), then returns the canonical "not configured" error. The backend doesn't have to know about S3-specific bucket-config concepts; the adapter handles them. When we add the GCS frontend, its adapter handles GCS-specific config probes the same way.

## The single-PR / one-direction-at-a-time discipline

shimanism is built one front, one back at a time, **but every service phase ships the full N × N matrix before moving to the next service**:
- Phase 1.4: AWS frontend, in-mem backend (foundation).
- Phase 1.5: domain refactor + MinIO backend.
- Phase 1.6: GCS backend.
- Phase 1.7: Azure Blob backend.
- Phase 1.8: K8s peer deployment.
- Phase 1.9 – 1.13: nuance + bug-fix + CI matrix.
- **Phase 1.14: GCS frontend.** Reuses the four backends.
- **Phase 1.15: Azure Blob frontend.** Reuses the four backends.
- Phase 1.16: full-matrix closer (3 frontends × 4 backends × 3 driver types = 36 driver-backend combinations green).

A service is not done until any cloud's tooling can drive it against any backend. Phases 2-8 follow the same N × N discipline for their service.
